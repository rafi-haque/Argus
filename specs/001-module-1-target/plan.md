## Summary
Automated web vulnerability scanner that discovers common vulnerabilities (SQLi, XSS, insecure headers) by understanding application context. Uses modular architecture with passive/active crawling, contextual attack orchestration, and developer-friendly reporting. Technical approach: Python CLI tool with pluggable modules, Playwright for JS rendering, and OWASP Juice Shop as test target.

## Technical Context
**Language/Version**: Python 3.11  
**Primary Dependencies**: requests, beautifulsoup4, playwright, argparse  
**Storage**: N/A (in-memory site map and findings)  
**Testing**: pytest  
**Target Platform**: Linux (Docker for OWASP Juice Shop test target)
**Project Type**: single (CLI security tool)  
**Performance Goals**: Complete scans in <15 minutes for apps with up to 200 endpoints, maintain <5 req/sec throughput  
**Constraints**: Support up to 500 endpoints and 2000 parameters, retry failed requests 3x with exponential backoff, include rate limiting and ethical safeguards  
**Scale/Scope**: Medium-scale web applications

**Implementation Phases** (from user input):
Phase 0: Foundation & Setup
   1. Set up the project structure in the argus/ directory.
   2. Initialize a Git repository.
   3. Set up a Python virtual environment (python -m venv .venv).
   4. Create the basic file structure: main.py, modules/, config/.
   5. Crucially: Set up your test target. Install OWASP Juice Shop via Docker. This is what 
      you will run Argus against.
   6. Write the initial README.md with the project's goal and a prominent Ethical Use 
      Disclaimer.

  Phase 1: The Simplest End-to-End Flow
   1. Goal: Make an HTTP request and check for one thing.
   2. Implement a basic CLI using argparse to accept a single URL.
   3. Build the Insecure Headers attack module. It's the easiest win.
   4. Build a rudimentary reporting engine that just prints findings to the console.
   5. Result: You can run python main.py --url http://localhost:3000 and it will tell you if 
      Juice Shop is missing security headers.

  Phase 2: Basic Crawling & Orchestration
   1. Goal: Find all links on a page and prepare to scan them.
   2. Build the passive crawler using requests and BeautifulSoup. It should take the seed URL 
      and discover all on-site links.
   3. Design and implement the "Site Map" data structure.
   4. Build the basic Scanning Orchestrator that loops through the Site Map and, for now, 
      just runs the Insecure Headers module on each discovered URL.

  Phase 3: The First Real Attack Module (SQLi)
   1. Goal: Detect a complex, server-side vulnerability.
   2. Build the Boolean-Based SQLi module. This will require you to implement a response 
      diffing utility.
   3. Integrate it into the Orchestrator. Start with a naive approach: run it on every 
      parameter.
   4. Test it against the login page and search bar of Juice Shop. Refine your detection 
      logic until it correctly finds the SQLi vulnerabilities.

  Phase 4: Introducing Context and Headless Browsing
   1. Goal: Make the scanner smarter and more powerful.
   2. Integrate Playwright. Augment the crawler so it can use the headless browser to find 
      more links and endpoints on JavaScript-heavy pages.
   3. Enhance the Orchestrator with the first contextual rules. For example: only run the 
      SQLi module on parameters that look like IDs or search queries.
   4. Build the Reflected XSS module.

  Phase 5: Advanced Detection & Reporting
   1. Goal: Polish the tool into a finished prototype.
   2. Implement the Time-Based SQLi module.
   3. Implement the DOM-Based XSS module using Playwright.
   4. Build the JSON reporting engine.
   5. Refine the CLI output to be clean and professional.
   6. Thoroughly document the project in the README.md with usage instructions and examples 
      of findings from Juice Shop.
